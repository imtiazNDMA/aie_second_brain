# Data Engineering for AI

The boring half of AI engineering. Models get the press; pipelines get the page-out at 3 AM. This synthesis maps the full data-engineering stack underneath an AI system — collection, cleaning, labeling, augmentation, feature storage, training/inference separation, monitoring, retraining — and where the LLM era changes (or doesn't change) the classical ML pattern.

## The lifecycle

```
[Sources]
   ↓
[[Data Collection]]    — ingest from web, logs, APIs, files, human annotators
   ↓
[[Data Cleaning]]      — dedup, normalize, fix encoding, drop bad rows
   ↓
[[Data Labeling]]      — human + programmatic + weak supervision
   ↓
[[Data Augmentation]]  — synthesize variants to expand coverage
   ↓
[[Data Pipeline]]      — orchestrated, scheduled, monitored flow
   ↓
   ├── [[Feature Store]] — precomputed features served to training and inference
   ├── Training data → model fine-tune / pretraining
   └── Embeddings → vector store ([[Vector Database Selection Guide]])
   ↓
[Model deployed] ([[Real-Time Deployment]] / [[Batch Deployment]])
   ↓
[[ML Monitoring]]       — drift, performance, data quality
   ↓
[[Continuous Training]] — retrain when monitoring fires
   ↓ (loop)
```

This pipeline is the centerpiece of *Designing Machine Learning Systems* ([[2026-04-12-designing-ml-systems]]). The LLM era ([[2026-04-12-llm-engineers-handbook]], [[2026-04-29-llmops-managing-large-language-models-in-production]]) keeps the skeleton but changes the inputs and the failure modes.

## What changes in the LLM era

| Stage | Classical ML | LLM systems |
| --- | --- | --- |
| Data Collection | Tabular, time-series, images | Documents, conversations, code, web crawl |
| Data Cleaning | Type coercion, missing values, outliers | PII removal, copyright filters, deduplication, content quality scoring |
| Data Labeling | Human annotation per row | Preference pairs (DPO), thumbs-up/down (KTO), verifiable rewards (RLVR) |
| Data Augmentation | Synthetic data, geometric transforms | Distillation from stronger teacher, paraphrasing, instruction tuning |
| Feature Store | Tabular features per entity | Embeddings per chunk; prompt templates as "features"; less central |
| Training data | Curated, finite | Pretraining: trillions of tokens; fine-tuning: 1K–1M samples |
| Monitoring | Accuracy / AUC / latency | + Hallucination, toxicity, faithfulness, prompt drift, eval scores |
| Retraining | Quarterly / monthly | Adapter swaps (LoRA), preference-data appends |

The biggest shift: **for foundation models, you don't own the pretraining data**. You own the *fine-tuning* and *evaluation* data — and that's where your engineering effort goes.

## Stage-by-stage guidance

### Data Collection

For LLM applications:
- **Production logs** — request/response pairs are the most underrated data source; instrument from day one
- **Curated public datasets** — UltraFeedback, ShareGPT, Open-Orca for SFT; HH-RLHF, UltraFeedback for preferences
- **Domain-specific scrape** — high-quality, license-clean documents
- **Synthetic data** — generated by stronger models; risk of bias amplification, must validate
- **Human annotations** — small but high-leverage; pair-rank, rubric-score, gold-standard answers

For RAG: the collection is the corpus. Quality of corpus dominates retrieval performance. See [[2026-04-29-rag-survey]] for systematic guidance.

### Data Cleaning

LLM-era essentials:
- **Deduplication** — exact + near-duplicate (MinHash); duplicates inflate train losses' pretty curves while hurting eval
- **PII / secret removal** — automated detectors + audit; legal-mandatory for many jurisdictions
- **Quality filtering** — fastText / classifier-based; remove SEO sludge, machine-translated junk
- **Format normalization** — encoding, whitespace, code-block markers
- **Toxicity / safety filtering** — domain-dependent; can be done at fine-tuning step instead

For RAG corpora: chunking is the cleaning. Chunk size, overlap, semantic boundaries — all decide retrievability. Standard defaults (512–1024 tokens with 10–20% overlap) work; better ones use semantic chunking or document structure.

### Data Labeling

The LLM era splits labeling into three regimes:

| Regime | Data shape | Use |
| --- | --- | --- |
| Pairwise preference | (prompt, chosen, rejected) | RLHF, DPO, ORPO |
| Pointwise rating | (prompt, response, label) | KTO, classifier training |
| Verifiable reward | (prompt, response, score from grader) | RLVR, GRPO |

Each has different annotation economics. Pairwise is what most public datasets use; pointwise is what production thumbs-up/down logs naturally produce; verifiable rewards are free if you have a grader. See [[LLM Alignment and Post-Training]] for which method consumes which.

### Data Augmentation / Synthetic Data

The 2024–2026 wave moved synthetic data from "nice to have" to "default":

- **Distillation** — generate (prompt, answer) from a stronger teacher; pure SFT
- **Self-instruct / Evol-Instruct** — model generates its own training prompts
- **Constitutional AI** — model critiques its own output against a constitution, generates corrections
- **RLAIF** — RLHF with AI-generated preference labels

[[Distillation]] specifically is the engine behind the s1 and DeepSeek-R1-Distill model families — it's how reasoning capability spreads from frontier to open-weights.

Risk: **bias amplification**. Synthetic data inherits and concentrates the teacher's blind spots. Always pair with held-out evaluation.

### Data Pipeline orchestration

Tooling, from the wiki's source coverage:

- **[[ZenML]]** — pipeline orchestrator used in [[2026-04-12-llm-engineers-handbook]]'s [[LLM Twin]] case study
- **[[Comet ML]]** — experiment tracking; pairs with ZenML
- **[[Opik]]** — prompt and evaluation monitoring
- **Airflow / Dagster / Prefect** — general-purpose orchestrators (no atomic page yet)
- **DVC** — data versioning (this repo uses it for `raw/source/` PDFs)

For free-of-cost / localhost deployments, the right starting point is local-first orchestration (Prefect or Dagster locally, or even just Make/scripts) plus DVC for data versioning. Add a hosted orchestrator only when team scale requires it.

### Feature Store (LLM-era reframe)

Classical [[Feature Store]] (Tecton, Feast) stores precomputed tabular features for online serving. In LLM systems:

- **Embeddings** are the new features; live in the [[Vector Database Selection Guide|vector store]], not a feature store
- **Prompt templates** are reusable assets; some teams store them in a "prompt store"
- **Few-shot example pools** — features-of-features; rotated in/out by retrieval
- **Tabular features still matter** — for hybrid systems mixing structured signals into LLM prompts

The [[Feature-Training-Inference Architecture]] pattern from the [[2026-04-12-llm-engineers-handbook|LLM Engineer's Handbook]] generalizes: split feature production from training from inference at clean interfaces, regardless of whether the "feature" is a tabular column or an embedding.

### Monitoring

[[ML Monitoring]] for LLM systems is fundamentally different — you can't just watch accuracy:

| Metric class | Examples | When to alert |
| --- | --- | --- |
| Latency / throughput | p50/p99 latency, tokens/sec | SLO breach |
| Cost | $ / request, tokens / request | Budget breach |
| Quality (offline) | RAG triad, FactScore, MT-Bench shadow runs | Score drop > X% |
| Quality (online) | thumbs-up rate, complaint rate, refusal rate | Trend break |
| Safety | Toxicity, jailbreak rate, PII leakage | Any positive |
| Drift | Prompt distribution, response distribution | Significant shift |
| Hallucination | Atomic-claim faithfulness, citation accuracy | Score drop |

Tools: [[Opik]] for trace/evaluation monitoring; [[AgentOps]] for agent traces; LangSmith / Helicone / Arize Phoenix in the broader ecosystem.

[[AIOps]] and [[LLM4AIOps]] (the discipline-flip in [[2026-05-09-llm-aiops-survey]]) are increasingly the operational frame — see [[AIOps-LLMOps Convergence for Agent Operations]].

### Continuous Training

Classical [[Continuous Training]] retrains on schedule or on drift. LLM-era variants:

- **Adapter retraining** — swap LoRA adapters; base model unchanged
- **Preference-data appends** — incremental DPO/KTO on new pairs
- **Index refresh** — re-embed and re-index corpus on update (RAG-side)
- **Prompt rotation** — prompt eng changes are the cheapest "retraining"
- **Full fine-tune** — rare; expensive; reserved for domain pivots

The cost gradient (cheapest → most expensive): prompt rotation < adapter swap < preference fine-tune < full fine-tune < pretrain. Pick the lowest tier that solves the problem.
