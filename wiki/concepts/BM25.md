# BM25

## Definition

**BM25** (Best Matching 25) is a probabilistic ranking function for lexical (keyword-based) document retrieval. It scores how well a query's terms match a document, balancing **term frequency** (more occurrences = more relevant, with diminishing returns) against **document length** (longer documents need higher term frequency to score equally) and **inverse document frequency** (rare terms across the corpus carry more weight than common ones). BM25 is the strongest non-learned baseline for retrieval and the canonical lexical side of [[Hybrid Search]] in modern RAG systems.

## The formula

For query $Q = \{q_1, \ldots, q_n\}$ and document $D$:

$$\text{BM25}(Q, D) = \sum_{i=1}^n \text{IDF}(q_i) \cdot \frac{f(q_i, D) \cdot (k_1 + 1)}{f(q_i, D) + k_1 \cdot \left(1 - b + b \cdot \frac{|D|}{\overline{|D|}}\right)}$$

where:

- $f(q_i, D)$ is the frequency of query term $q_i$ in document $D$
- $|D|$ is the document length (in tokens)
- $\overline{|D|}$ is the average document length in the corpus
- $\text{IDF}(q_i)$ is the inverse document frequency: $\log\left(\frac{N - n(q_i) + 0.5}{n(q_i) + 0.5} + 1\right)$
- $k_1$ controls term-frequency saturation (typical: 1.2–2.0)
- $b$ controls length-normalization strength (typical: 0.75)

## Why each piece matters

- **Term frequency saturation** ($k_1$) — a document with 10 occurrences of a term isn't 10× as relevant as one with 1; the formula's denominator caps the contribution of repeated terms
- **Length normalization** ($b$) — penalizes long documents that mention every term incidentally; a short document mentioning the term gets a relative boost
- **IDF** — common terms ("the", "and") get near-zero weight; rare terms ("tokenization", "QLoRA") dominate scoring

The combination is what makes BM25 robust across heterogeneous corpora without per-domain tuning.

## Where it fits

BM25 is the canonical lexical retriever in:

- **Elasticsearch / OpenSearch** — default scoring function
- **Lucene / Solr** — default since 6.0
- **Postgres `tsvector` / `pg_trgm`** — implementations vary; rank by similar principles
- **[[Weaviate]], [[Qdrant]], [[Pinecone]], [[Meilisearch]]** — sparse / hybrid mode often uses BM25 or a learned variant
- **Standalone Python** — `rank_bm25` library; trivial integration

## When BM25 wins over vector search

| Scenario | Why BM25 wins |
| --- | --- |
| Exact-match queries | Vector embeddings smear specific tokens; BM25 preserves them |
| Acronyms, version numbers, error codes | Same — embeddings lose precision on rare tokens |
| Identifier-heavy domains (code, SKUs, IDs) | Lexical match is the point |
| Cold start (no labeled data for fine-tuning embeddings) | BM25 is unsupervised |
| Auditability / explainability | "Why did this document rank?" — BM25 is term-weight-explainable |

See [[Hybrid Search]] for the standard pattern of pairing BM25 with vector retrieval.

## When it loses

- **Paraphrased queries** — "how to fine-tune" vs. corpus's "domain adaptation"
- **Cross-lingual retrieval** — no shared tokens
- **Conceptual / abstract queries** — "what makes a model robust?"
- **Synonyms and morphology** — "cars" vs. "automobile"; some of this is mitigated by stemming / lemmatization

These are exactly the cases vector search handles, which is why hybrid is the production default.

## Modern variants

- **BM25F** — handles documents with multiple fields (title, body, metadata) with per-field weights
- **BM25+** — adjusts the lower-bound contribution of terms in long documents
- **SPLADE** — neural sparse encoder that produces BM25-like sparse vectors with learned term weights
- **uniCOIL** — another learned sparse encoder
- **Atire BM25** — engineering variant for very large corpora

For most use cases plain BM25 is fine; learned sparse variants (SPLADE family) are worth adopting when you have query-document supervision data and care about the last 5–10% of relevance.

## Hyperparameter tuning

The defaults ($k_1 = 1.2$, $b = 0.75$) are robust across corpora, but slight tuning helps:

- **Short documents (tweets, FAQ entries)** — try lower $b$ (around 0.3–0.5)
- **Long documents (papers, books)** — defaults work well
- **Heterogeneous lengths** — BM25F per-field weights matter more than $b$ tuning
- **Term-heavy queries (technical docs)** — try higher $k_1$ (1.5–2.0) so repeated technical terms reinforce

Always measure on held-out queries; don't tune blind.

## Why it's still relevant in the LLM era

LLMs replaced rule-based pipelines for ranking and reranking, but they didn't replace BM25 for first-stage lexical retrieval. The reasons:

1. BM25 is fast, sub-millisecond per query at corpus sizes where vector search starts to slow down
2. BM25 produces well-calibrated scores for hybrid fusion ([[RAG-Fusion]], RRF)
3. BM25 is unsupervised — no labeled data needed
4. BM25 nails exact-match queries that embeddings systematically lose

In 2026, the typical RAG retrieval stack is: BM25 + dense embedding + RRF → cross-encoder rerank ([[Reranking]]) → LLM generation. BM25 is the cheapest layer and often the highest-precision contributor for technical content.
